# Moka recipe — research findings (ticket 01)

Source: full clone of https://github.com/millionco/moka (79 commits, study date 2026-08-01) + https://million.dev/moka. File citations are repo-relative paths in that clone.

## Summary

- Moka v1 is a **105,353-param CNN** (32-ch stem, 12 nested-bottleneck resblocks, 3 zero-init global-context adapters) for 9×9 Go, shipped as **113,648 bytes of per-output-channel symmetric INT8** (≈101 KB gzipped) plus a **~4 KB hand-rolled JS conv runtime in a Web Worker** — no ONNX, no wasm-bindgen.
- The heavy lifting is **not one big training run**: 50k–450k teacher positions got it to ~16/100 wins vs KataGo; the jumps to 47% (95/200) came from **many small arena-gated micro-updates** — DAgger on-policy rounds, distillation from its own 64-visit search on 4k-position corpora, critical-regret QAT, zero-init adapter fine-tunes, and checkpoint soups.
- **QUAT matters**: they train float, materialize an "exact INT8" checkpoint (straight-through fake-quant), arena-test *the exported bytes*, and use the quantized model as the preservation reference. INT8 was measured lossless (~0 game delta) at 100k params; naive INT4 destroyed it, mixed INT4-trunk/INT8-heads changed ~20% of greedy moves → rejected.
- Data hygiene that made iteration legible: **split by whole game** (game_id % 10), on-policy data only in train buckets, fixed 20-game dev screen then **two independent 100-game confirm blocks vs the teacher**, selection by validation loss.
- The 47% headline is **weights + search**: raw greedy policy peaked near 16–20/100; the deployed player runs 64-visit PUCT with full 8-way symmetry ensembling at root *and* descendants, FPU reduction 0.5, PUCT exploration 1.75, value weight 1.25.

## Findings

### 1. Net architecture (`model/go-model.json`, `python/go_model/model.py`, `python/go_model/config.py`)

- **Input:** 12 binary/scalar planes on 9×9 (`features.py:encode_moka_features`): current-player stones, opponent stones, 1-liberty groups (each color), 2-liberty groups (each color), ko point, previous move, move before that, pass on previous turn (whole-board plane), pass two turns ago (whole-board plane), perspective-komi constant plane (`komi/15`). An alternate 16-plane "context" encoder (5 recent moves, move-count plane) **lost in arena** and was rejected.
- **Trunk:** 3×3 conv 12→32 + ReLU; then 12 `NestedBottleneckBlock`s: 1×1 reduce 32→16, 3×3 conv 16→16, 3×3 conv 16→16, 1×1 expand 16→32, residual add + ReLU (`NESTED_RESIDUAL_BLOCK_COUNT=12`, `TRUNK_CHANNEL_COUNT=32`, `NESTED_BOTTLENECK_CHANNEL_COUNT=16`).
- **Global adapters:** every 4th block (3 total) inserts a zero-initialized adapter after the first spatial conv: mean+max spatial pool → Linear 32→8 → ReLU → Linear 8→16 broadcast as a per-channel bias (`GlobalNestedBottleneckBlock`, `GLOBAL_RESIDUAL_HIDDEN_CHANNEL_COUNT=8`, interval 4). Zero-init means it loads identically onto the incumbent net; added exactly 1,224 params (final 105,353). This was the last accepted architecture change and won 95–78 over 200 confirm games (log 2026-07-28 "Quantized global residual context").
- **Heads:** policy = 1×1 conv 32→4, flatten 4·81=324, Linear 324→**82 logits** (81 points + pass). Value = 1×1 conv 32→2, flatten 162, Linear 162→32, ReLU, Linear 32→1, tanh (current-player, ±1).
- Sweep results worth copying (log "Fixed protocol and compact-network sweep", 100-game dev arena): plain 4-block trunk 90k params → 2/100; 12-block nested-bottleneck with pure soft targets → 9/100; **nested + 50% hard targets → 16/100** (first real incumbent); wide (190k params), recurrent, spatial-only policy, and context-planes variants all worse. The bottleneck trick (more, narrower blocks) beat wider nets at equal budget.

### 2. Weight budget: how 101 KB happened (`python/go_model/export.py`, `python/go_model/quantization.py`, log "Four-bit quantization")

- **Scheme:** symmetric INT8 **per output channel** for every conv/linear weight: `scale_c = max|w_c| / 127` stored as float32 per channel; `w_q = round(w/scale)` clipped to ±127. **Biases stay float32.** Total float32 bytes = 4,740 (60 bias tensors); everything else 1 byte/param. (`export.py:271–303`)
- **Packing:** one flat `.bin`; each tensor's data chunk 4-byte-aligned (`append_aligned`), then its float32 scales chunk; a JSON manifest records per-tensor `dataOffset/scaleOffset/shape/dtype`, architecture, sha256, total byte count. Browser verifies the digest. Shipped: `go-model.bin` **113,648 B**, `go-model.json` 16,198 B. Deterministic gzip = **100,653 B** (≈ the "101 KB" on million.dev; README rounds raw bytes to "114 KB"/"100 KB").
- **Budget enforcement:** `MAXIMUM_MODEL_BYTES = 200_000` hard error in exporter; they used ~57% of it.
- **QAT:** during training/continuations, weights pass `fake_quantize_int8_weight` (round-to-nearest per-channel with **straight-through gradient**, `quantization.py:10–26`). "Exact INT8" materialized checkpoints are what actually play arena games; INT8-vs-float delta measured at ~1 game per 100 (log "Full-network distillation… INT8 deployment-format gate": 86 vs 91 wins over 200).
- **INT4 experiment (rejected):** nibble-packed, 2 values/byte, groupwise scales per 16/32/64 values. All-INT4 group-16 = 83.9 KB but top-move agreement 65.7% (vs ~80% INT8). Best mix (INT8 stem+heads, INT4-trunk group-64 ≈ 79.7 KB) still flipped ~20% of greedy moves → "not release quality", kept as exporter option only (`--quantization-bits 4`, `INT4_GROUP_SIZE=16`).
- **"Mixed INT8/INT16"** on million.dev refers to the *earlier* website artifact (`4a58dcfd`, 138,616 B raw, 2026-07-27 "Website promotion"); `MODEL_POLICY_QUANTIZATION_BITS=(8,16)` in config is the leftover knob. Current v1 (`35c1e51c…`, which is exactly what million.dev serves) is uniform INT8 + f32 scales/biases. INT8 was sufficient *because* of QAT — don't read the landing page as "you need INT16".
- **Adapter-only QAT (key late-stage move):** quantize the whole frozen net every forward pass but backprop only into the 12 new adapter tensors (`train.py` `train_global_residual_adapter_changes_only` path + `fake_quantize_int8_parameters`); lr 1e-5, 3 epochs, 5,167 teacher rows → +17 wins/200. The float-shadow checkpoint matched the deployed net's moves only 51.1% on one bucket while the exact-INT8 shadow matched 75.6% — so they **quantize the preservation reference too**.

### 3. Teacher data and sampling (`python/go_model/generate.py`, `collect.py`, `teacher.py`, log passim)

- **Teachers:** (a) KataGo **b6c96** generalist (1,026,510 params, ONNX via single-thread CPUExecutionProvider); (b) native 9×9 specialist **kata9x9-b18c384nbt** (28.9M params, PyTorch/Metal) for stronger labels and search-based reanalysis. Teachers only exist at data-generation time.
- **Primary corpus:** teacher self-play one position per ply, moves **temperature-sampled** from teacher policy with `T = max(0.35, 1.15 − ply/100)` (early diversity, late sharpness), no pass before ply 20, reset at game end; default 50,000 positions (`generate.py`, `DEFAULT_POSITION_COUNT=50_000`). Stored as float16 npz: features(12×9×9), full 82-way policy, value, game_id.
- **DAgger on-policy (`collect.py`, biggest single method win):** roll out the *current student* (temp 0.85 sampling over legal moves); on student's own-color turns, teacher **intervenes with p=0.15** to rescue bad trajectories; teacher labels **every reached state** with full policy + value. Sample weight = Goldilocks: `0.25 + 1.75·exp(−0.5·((d−0.55)/0.25)²)` where `d = 1 − P_student(teacher's top move)` — i.e. up-weight middle-difficulty positions, down-weight solved and hopeless ones. Volumes: first round 10k on-policy + 10k replay (−11.7% test loss, +4.6 pt agreement); later 100k on-policy. Distribution-shift is real: baseline student agreed with the teacher on only **36.9% of its own rollout states** vs ~47% on teacher self-play states.
- **Later corpora (where the real strength came from):** self-play *games* of the student under its own 64-visit search vs teacher, keeping only student decision positions — corpora of just **4,246 / 4,491 positions** blended 75% search-visit distribution + 25% symmetry-averaged root policy, trained 1 epoch at lr 5e-6 with a 0.25 policy-preservation penalty + 20k on-policy replay → +7 wins/200, accepted; repeating the round did **not** compound (log "Full-network distillation from the accepted search player", "Repeated full-network search distillation"). **Critical-regret corpora**: collect roots where the student's played move had highest teacher action-regret (top 12.5% + 12.5% uniform), 8-fold replay, **policy-linear tensors only**, exact-INT8 forward → +4/300.
- **Data scale failed on its own:** 300k fresh specialist positions + 150k replay trained from scratch → 5/100 (*regressed* below the 16/100 incumbent). Lesson recorded in log "Data scale and continuation": sequential error accumulation isn't fixed by volume; on-policy correction beats volume.
- **Splitting:** `game_id % 10` → bucket 0 = validation, bucket 1 = test — **whole games together**, never per-position, to prevent correlated leakage; supplemental on-policy sets are masked into train buckets only.

### 4. Distillation targets and losses (`python/go_model/train.py`)

- Defaults: **AdamW lr 1e-3, batch 256, 20–30 epochs** from scratch; continuations lr 5e-6…3e-5 for 1–3 epochs; validation-loss checkpoint selection (`TRAIN_SELECTION_LOSS="loss"`). **Random 8-way symmetry augmentation per batch** (`apply_batch_board_symmetry`, batched 4.4× faster than per-sample loop).
- **Policy:** cross-entropy against the teacher's full soft distribution, with `hard_policy_weight=0.5`: targets = 0.5·teacher_dist + 0.5·one_hot(teacher argmax). The 50% hard mix was the single biggest bucket-1 win (9/100 → 16/100); 80% hard regressed. Ablation table of rejected alternatives: pure reverse KL 7/100, α–β divergence 5/100, top-4 truncation 12/100.
- **Value:** MSE on tanh value (±1), weight 0.5; teacher value = current-player win prob mapped from KataGo's W/L logits; short-horizon value blending (0.25) used when available.
- **Aux scaffolds (train-time only, not exported):** listwise Plackett–Luce ranking over teacher's top-8 moves, ownership MSE (0.25), score-margin MSE (0.1), child-Q auxiliary, attention transfer (0.1), soft-policy head at T=4 (weight 8). Each logged separately; most gave small or no arena gains alone.
- **Anti-forgetting on continuations:** `policy_preservation_weight=0.25` MSE between current and frozen *quantized* incumbent logits; old corpora replayed alongside new.
- **GRPO explored:** group-relative outcome RL needed dense teacher distillation folded in (weight 0.2) to gain at all (19/100); a second iteration regressed. RL is a seasoning here, not the meal.
- **Checkpoint soups:** averaging 2–5 same-lineage fine-tuned checkpoints (only adapter tensors differed) was accepted twice (+13 and +13 wins/200); interpolated soup selected purely on held-out loss, confirmed in arena.

### 5. The ~6 KB browser runtime (`src/runtime.ts`, `src/worker.ts`, `src/client.ts`, `RESEARCH.md` "Browser runtime decision")

- Plain TypeScript, **no library**: direct 3×3 conv loop over NHWC `Float32Array` (padding via bound checks), ReLU, Linear, mean+max pool, tanh. The whole inference file is 434 lines; compiled/minified worker ≈ **4,267 B** (1.6 KB gz). Landing page's "6 KB" is the same worker at a slightly different build.
- **Dequantize once at load**: worker manifest+bin fetched (sha256 checked), every INT8 tensor expanded to Worker-owned `Float32Array` (~400 KB RAM); steady-state inference is pure float math on typed arrays — 9.0 ms mean single-position on Apple Silicon, including messaging.
- Web Worker keeps it off the main thread; policy logits returned via **transferable buffer** (zero-copy); site defers model load to 1.5 s after hydration via idle callback, immutable 1-year cache on the fingerprinted bin.
- They **built the Rust→WASM alternative** (`wasm/src/lib.rs`, ~9.3 KB raw, no wasm-bindgen, alloc/ReLU/dense kernels) and deliberately didn't ship it: JS/WASM boundary crossings per layer erase SIMD gains on tiny tensors — ship only if an *end-to-end* benchmark wins ("Custom WASM kernels: add only if measured faster"). WebGPU rejected a priori (dispatch overhead ≫ compute at this scale).
- Optimization decision table (RESEARCH.md): ONNX Runtime WASM ~16 MB → rejected; custom worker JS = default; custom WASM = only if faster; WebGPU = only if faster.

### 6. Hardware / time

- Everything on one **Apple Silicon laptop**: MLX 0.32 (training), Python 3.12 via `uv`, ONNX Runtime CPU for the b6c96 teacher, PyTorch/Metal for the b18 specialist; Chromium for arena/browser benchmarks (`experiment-log.md` Environment, 2026-07-26).
- Whole arc = **4 days, 2026-07-26 → 07-29, 79 commits**, dozens of gated experiments/day. A 100-game Python arena block ≈ **100–460 s** depending on visits (64-visit search ≈ 300–460 s; raw policy ≈ 100 s). Compiled MLX inference 0.31–0.37 ms/position. Capacity: all training (≤450k positions, ≤105k params, ≤30 epochs) is minutes-per-run scale — no cluster anywhere, no training-time complaint in 5,327 log lines. Teacher position generation with the 1M-param b6 teacher on CPU was fast enough to produce 300k positions per batch job; the 28.9M-param b18 went through a 16-thread analysis server with query batching (`SEARCH_TEACHER_*` config).

## Implications for makruk

**Transfers directly:**

1. **The shape of the program**: small fixed CNN, distilled from the strongest available teacher (fairy-stockfish full skill = our KataGo), per-channel INT8, hand-rolled dequantize-once inference. At 1 byte/param, makruk's 0.5–1 MB budget = **500k–1M params — 5–10× Moka's net**. Makruk's 8×8 board is *smaller* than 9×9 and has fewer legal moves; trunk params are board-size-invariant (convs), so we can afford 48–64 trunk channels, 16–20 nested blocks without blinking.
2. **DAgger loop with teacher intervention + Goldilocks weighting** — this was Moka's first big jump (2/100 → 9/100) and generalizes cleanly: play our net vs fairy, label every reached position with fairy's eval + bestmove (multi-PV!), up-weight mid-difficulty positions. Stockfish gives sparse targets (one bestmove + eval) where KataGo gives a dense 82-way policy; **use multi-PV (k=4–8) with depth-scaled soft targets** to approximate a dense distribution, or accept a mostly-hard target and lean on Moka's finding that 50% hard + 50% soft beat pure soft.
3. **Split by game, dev-screen then two confirm blocks, arena-test the exported quantized artifact** — maps 1:1 onto `scripts/match-arena.mjs`. Their gating discipline (nothing ships that doesn't win both independent 100-game blocks) is why 4 days of iteration compounded instead of churned.
4. **QAT with straight-through INT8, and quantize the reference model too** — they measured float-vs-INT8 move agreement of 51% vs 76% on one bucket; always tune/eval against the quantized artifact. Our repo already demands roundtrip-exact `do_move`/zobrist; add "INT8 artifact == float checkpoint move match" as a required gate.
5. **Zero-init adapter fine-tunes + checkpoint soups on a frozen quantized trunk** — the cheapest late-stage gains (+30 wins/200 combined for ~1.2k params). Very applicable: add 2–3 global-context adapters (piece-count/counting-state pooled context is *global* information in makruk!) to a frozen trunk and QAT-train only those.
6. **Forced-promotion simplification**: makruk has no under-promotion (bia→met only, in-zone), so policy = pure from→to = 64×64 = 4,096 logits, no promotion planes needed (the `m` suffix is output *format*, per AGENTS.md, not a policy dimension).

**Needs adaptation (net shape):**

7. **Policy-head parameter trap**: Moka's flat Linear(324→82) = 26.5k params works because Go's action space = squares. Naively flattening 4×64 → 4,096 = ~1M params — the head would dwarf the trunk and eat the budget. Two budget-safe options: (a) **displacement-plane head** (AlphaZero-style): makruk has no diagonal sliders (met/khon are 1-step diagonal), so the move geometry is 28 rook-ray planes + 8 knight + ~4 diag-1 + 1 forward ≈ 41 planes → 1×1 conv 32→41 = 1,312 params, 2,624 outputs; (b) factorized from-head/to-head spatial logits combined over legal moves. Option (a) is cleaner and small.
8. **Input planes**: replace liberties/ko/komi with makruk planes — side-to-move pieces by type (12 planes: 6 types × 2 colors, perspective-encoded), promotion-zone marker (constant plane), **counting-rule planes** (moves-remaining normalized, who-holds-counting-rights flag; the site's counting rule *decides games*, and a value net blind to it will bleed draws — mirrors Moka's komi plane but it's materially load-bearing here), maybe 1–2 history planes for repetition awareness.
9. **Value target is WDL not score**: makruk outcomes are win/draw/loss (draws via counting rule + repetition + stalemate) — use a 3-way WDL head or tanh with 0 for draw; Moka's ownership/score-margin auxes don't map. Repetition handling must live in the search/ adjudication (AGENTS.md already forbids game-level repetition adjudication in search), not be baked into training targets.
10. **Symmetry**: Go has 8 D4 symmetries; makruk preserves only **4** (identity, horizontal mirror; and rank-flip+color-swap since the promotion zone is rank-based) — file-transpose is invalid (promotion zones would map to files). Use 4-way augmentation, not 8.

**Doesn't transfer:**

11. **The JS runtime itself** — makruk already has a Rust/WASM engine with pinned wasm-bindgen; inference belongs in *that* (dequantize-on-load → f32 arrays, same idea). Moka's "JS beats wasm for tiny nets" finding is a caution against adding a *separate* JS runtime, not against our existing wasm path. The no-modules classic-worker constraint we have (AGENTS.md) is stricter than their module-worker setup — keep it.
12. **KataGo-specific machinery**: liberties, ko, komi, ownership, area scoring, pass handling, seki adjudication — all Go-only. Their PUCT/symmetry-ensemble search is Go-tuned; our search is alpha-beta with the net as eval/ordering (Moka also confirms raw-policy-only play is weak: 16–20/100 — so plan for the net to serve *inside* search, not replace it; their own 47% number required 64 visits of search on top of the distilled net).
13. **"Just add data"**: Moka's most replicated negative result — 300k fresh positions made things *worse*. Expect the same for fairy-labeled positions. Budget compute for **iterated small on-policy rounds** (generate → correct → 1-epoch continuation → gate), not one monolithic dataset.

**Practical scale estimate for a makruk v1:** ~30 input planes ·8×8, 48-ch trunk, 12–16 nested blocks (24-ch bottleneck), 2 global adapters, displacement-plane policy head (41 planes), WDL value head ≈ **200–350k params → 200–350 KB INT8** — comfortably under the 0.5 MB floor of the budget, leaving headroom to double if arena gates justify it. Training is laptop-scale (Moka ran everything on one Apple Silicon box in minute-scale runs; PyTorch on a single GPU or even CPU is adequate at this size).
